1. ARCHITECTURE AND IMPLEMENTATION CHOICES
Frontend: React + TypeScript + Vite + Tailwind (role-aware views and validated forms).
Backend: Python FastAPI with modular services in one demo deployment.
Data: SQLite demo with migration-ready schema; private file store for source PDFs/images and CSVs.
Finance/maths: Python Decimal for INR; separate kWh precision and rounding rules; simple deterministic tariff/settlement adapters; optional PuLP/OR-Tools or an enumerative constrained-plan solver for the 20-household demonstration.
OCR: reviewed extractor for PDFs/images, with manual correction mandatory before extracted values become verified household inputs.
Exports: text/CSV/PDF internal reports where feasible; every report explicitly identifies assumptions and whether figures are estimated, imported, confirmed or reconciled.
Integrations: manual entry and source-labelled CSV imports. No live inverter or DISCOM API is required or represented as functional.

5. VNM READINESS / APPROVAL BOUNDARY (F02, F06)
- Minimal sourced rule registry: jurisdiction/DISCOM, connection type, applicable date, known requirement, evidence URL/document and review status.
- Output states are informational: REQUIREMENTS_NOTED, POTENTIAL_ISSUE, NEEDS_VERIFICATION, APPROVAL_EVIDENCE_RECORDED.
- Only genuine external evidence may set a project as having DISCOM approval. Synthetic demo approvals must be visibly marked synthetic in UI and data.
- Do not calculate officially approved household credits without a valid allocation version and adequate settlement evidence. Hypothetical planning calculations are explicitly marked 'modelled'.

6. FEASIBILITY / PROJECTION ENGINE (F04)
Capacity candidates limited by usable roof area and explicit density/technical assumptions. Monthly estimated generation (kWh) = capacity (kW) x location/month-specific yield (kWh/kW), with losses/uncertainty disclosed.
Project cost = documented initial quoted cost + included design/other costs, with financing and O&M treated separately as specified.
Model creditable electricity only using the selected metering and settlement scenario; never set export equal to generation without an explicit justified project configuration.
Use historical household kWh to estimate possible benefit realisation and carry-forward, without assuming that every unit of household consumption can be offset identically.
Recompute and version snapshots when provider quote changes. Show stale-plan alerts for prior calculations.

7. BENEFIT-AWARE OPTIMISER (F05)
Inputs: confirmed household budget ceilings, optional demand history, capacity/cost scenarios, consent/eligibility flags, financing terms, O&M, solar yield, permitted ownership/credit-share treatment, assumed credit valuation and carry-forward/settlement rules.
Variables (for selected model): x_i participation (0/1), upfront contribution a_i, financed amount d_i, monthly payment m_i, ownership share w_i; optional capacity choice K.
Core constraints:
  - 0 <= a_i <= max_upfront_i; 0 <= m_i <= max_monthly_i.
  - No nonconsenting or disallowed participant is silently included.
  - Accepted project financing/equity sources fund the full project cost, with fees and interest consistently treated.
  - Sum of active ownership fractions = 1 subject to declared rounding; approved allocations follow permitted ownership/credit rules and approval state.
  - Capacity fits stated roof and technical limits; no unsupported cross-meter transfer.
Comparison baselines: (a) equal upfront/investment shares, (b) affordability-aware participant-constrained plan, (c) benefit-aware plan using projected individual net return, payback and downside stress alongside inclusion.
Candidate objective: maximise financially feasible participation subject to documented minimum benefit or acceptable risk constraints where such preferences are actually supplied; then report trade-offs in total projected benefits, payback and residual funding. If a preference/threshold is not supplied, show outcomes without asserting they satisfy that person's unstated preference.
Constraint solver: enumerative search for small fixed demos or MILP where helpful. Return status: FEASIBLE, INFEASIBLE, TIMEOUT, OPTIMAL_PROVEN where applicable. Independently check the solver output.
What-If scenarios copy baseline snapshot, change member withdrawal, installation cost or yield, recompute outcomes, preserve baseline and explain differences.

8. CONTRIBUTIONS, OWNERSHIP, APPROVALS (F06)
Suggested transitions: DRAFT_PLAN -> HOUSEHOLD_ACCEPTED -> SOCIETY_CONFIRMED -> SUBMITTED_TO_DISCOM -> DISCOM_APPROVAL_EVIDENCE_RECORDED -> COMMISSIONED -> SETTLEMENT_IMPORTED -> RECONCILED.
The transition labels describe records stored in Solaris, not actions Solaris carries out on behalf of an authority. Do not advance to official-approval-labelled states without evidence. Store effective dates, who approved and document references. Changes invalidate affected projected or reconciled snapshots as appropriate.

9. CREDIT RECONCILIATION (F09)
Data inputs: resident-reviewed post-installation bill, active approved allocation for a matched settlement period, credible eligible settlement figures, previous carry-forward/adjustments and the applicable rate/credit treatment.
Algorithm:
 A. Verify sources and align billing/settlement periods. If dates mismatch, request a defensible reconciliation or leave the result pending; do not blindly prorate with no policy support.
 B. Establish expected eligible credit for the participant using approved allocation and settlement rules; if not possible, return UNVERIFIABLE.
 C. Compare like-for-like units and monetary values. Track opening, allocated, applied, carried-forward, settled and closing credits independently when data supports them.
 D. Check OCR corrections, share-effective-date, carry-forward and billing-period issues before recording an unexplained gap.
 E. Produce a report with source document IDs, rule version, calculation and status EXPLAINED / UNRESOLVED / UNVERIFIABLE.
Do not equate a discrepancy with DISCOM error; do not use gross PV output as the authoritative expected household credit.

10. FINANCIAL LEDGER AND PROJECTED-VS-ACTUAL (F08, F10)
Keep distinct (a) one-time upfront contributions, (b) financed principal actually disbursed, (c) loan principal payments, (d) interest/fees, (e) O&M, (f) bill-credit benefits and (g) end-of-period adjustments/carry-forward.
Monthly household cash flow during repayment is the recorded bill-credit financial benefit minus actual loan payments and operating contributions; upfront investment is included at the original payment date. Do not subtract full financed investment again if repayments are already counted as outflows.
Simple payback may use total capital cost divided by an assumed constant annual benefit with caveats; cash-flow break-even uses dated actual/projected contributions, repayments, costs and benefits. Mark where payback cannot be determined meaningfully.
F10 compares historical locked projection assumptions to aligned realised months, with source-supported explanation flags and recalculated future estimates. Do not rewrite the original plan when the forecast is refreshed.

11. SECURITY / FILE PROCESSING
- Authorisation enforced for each organisation, project, household, file, report and provider assignment at the backend.
- Store bills and consented budget information privately; mask account numbers; restrict provider access to project scope.
- Validate files by MIME, extension, size and document safety; never trust OCR outputs without confirmation.
- Auditable change log for acceptance, rule versions, provider quotes, approvals, imported settlement, reconciliation and projected financial returns.
- Use synthetic, anonymised example source documents for any public demo.

12. TESTS / QUALITY GATES
Unit: kW/kWh/INR conversions, interest schedules and instalments, projected vs actual maths, share totals and rounding, carry-forward, negative/zero inputs, double-count protection.
Property: no feasible plan exceeds a household maximum or budget funding limit; shares reconcile to 100% when required; scenario edits cannot mutate baseline.
Integration: role separation, household intake and OCR confirmation, quote update triggers recalculation, approval evidence gating, post-install bill to F09 to F08/F10 flow.
Negative cases: no credible settlement; period mismatch; surplus credits; stale allocation; duplicate bills; contradictory OCR; unapproved model; project/member privacy violation.
Demo: use reproducible ~20-household synthetic project, clear regulatory assumptions and complete F01 -> F10 narrative.
